# Vivo — Whoop OAuth relay

A tiny, stateless Cloudflare Worker. Its only job is holding the Whoop OAuth
client secret, which cannot live in Vivo's client-side code (see
`vivo/ARCHITECTURE.md` for why). It stores nothing — no database, no KV —
and forgets every request the moment it's answered.

## Deploy it (no CLI needed — dashboard path)

1. Go to [dash.cloudflare.com](https://dash.cloudflare.com) → **Workers & Pages** → **Create** → **Create Worker**. Free plan is enough.
2. Give it a name (e.g. `vivo-whoop-relay`) → **Deploy** (this deploys Cloudflare's placeholder code — you'll replace it next).
3. Click **Edit code** (the Quick Edit / dashboard code editor). Delete the placeholder and paste in the full contents of `worker.js` from this folder. Click **Deploy**.
4. Go to the Worker's **Settings → Variables and Secrets**:
   - Add variable `ALLOWED_ORIGIN` = `https://thejacobbarney.com` (plain text)
   - Add variable `WHOOP_API_BASE` = `https://api.prod.whoop.com/developer/v2` (plain text — see note below)
   - Add variable `WHOOP_CLIENT_ID` = *(the Client ID from your Whoop developer dashboard)* — mark as **Encrypt**
   - Add variable `WHOOP_CLIENT_SECRET` = *(the Client Secret)* — mark as **Encrypt**
   - Save / redeploy if prompted.
5. Note the Worker's URL — it'll be something like `https://vivo-whoop-relay.<your-subdomain>.workers.dev`. Send that to me (or drop it in `vivo/js/whoopAuth.js`'s `RELAY_BASE_URL` yourself) so the frontend knows where to call.

## Deploy it (CLI path, if you'd rather)

```
npm install -g wrangler
cd whoop-relay
wrangler login
wrangler secret put WHOOP_CLIENT_ID
wrangler secret put WHOOP_CLIENT_SECRET
wrangler deploy
```

`wrangler.toml` already has `ALLOWED_ORIGIN` and `WHOOP_API_BASE` filled in —
edit them first if either needs to change.

## Register the redirect URI with Whoop

In the [Whoop developer dashboard](https://developer-dashboard.whoop.com) for
this app, add this exact redirect URL:

```
https://thejacobbarney.com/vivo/oauth-callback.html
```

Whoop rejects any redirect that doesn't exactly match what's registered,
including trailing slashes, so copy it exactly.

## A note on `WHOOP_API_BASE`

Whoop's public documentation wasn't reachable from the environment this was
built in (blocked by network policy), so the exact current data-endpoint
paths and response field names are a best-effort guess based on secondary
sources, not verified against Whoop's live API or official docs. `/developer/v2`
is this Worker's default; `vivo/js/parsers/whoopApi.js` is where the actual
endpoint paths it calls (`/proxy/cycle`, `/proxy/recovery`, etc.) are defined,
and where field-mapping bugs will show up first once you do a real test
connection in Sandbox mode. If the first real connection comes back with
different field names or a 404 on a path, that's expected — send me what you
see and I'll fix the mapping against real data rather than documentation I
couldn't load.

## Why a Worker and not something simpler

Whoop's OAuth2 token exchange requires `client_secret_post` authentication —
there's no documented PKCE/public-client option that would let this happen
entirely in the browser the way the rest of Vivo works. This Worker is the
smallest server-side footprint that satisfies that requirement: it holds the
secret, forwards exactly three request shapes to Whoop's own API, and keeps
no state of its own. The actual Whoop access/refresh tokens are generated by
Whoop and stored only in the browser's `localStorage`, same as Vivo's
existing Anthropic API key pattern.
